# Cost guards instead of approving infrastructure changes

Agent runs deploy infrastructure changes to the `portfolio` account without human approval. We first planned to require approval whenever a deploy created, deleted or replaced AWS resources. We dropped that because what we actually feared was a runaway bill, not the changes themselves. Four guards contain cost instead. The Foundation creates the last three in AWS:

1. **Estimate:** CI runs Infracost on every ready pull request, comparing the Terraform files in the PR with its base. It needs no plan and no AWS login, and only that step receives the Infracost key. If the estimated monthly cost increase is more than $1, or the estimate can't be made, the deploy waits for approval in a GitHub environment. Otherwise it deploys by itself. Infracost prices fixed-cost resources reliably and prices pay-per-use services (Lambda, DSQL) as $0, so the guards below catch usage runaways. This gate lives in the workflow file, which a run's token can't edit, but AWS can't tell whether the check ran. The three guards below sit outside the repo, where a run can't change them.
2. **Prevent:** a Service Control Policy on each member account denies every AWS service that isn't on that account's allowlist. NAT Gateways, EC2 instances, RDS, ElastiCache and load balancers aren't on either list, so a deploy that tries to create one fails immediately. This enforces ADR-0002 in AWS itself. An allowlist replaced an earlier list of denied actions, because a denylist lets through every route nobody thought of. It limits which services run, not how much they're used, so the guards below still matter. The cost is that a service missing from the list also fails for running Lambdas, so an episode's Setup adds any new service before its run, and the feature is tested before it reaches production. The same SCP limits member accounts to `ap-southeast-1`. Global services are exempt, and so is ACM, because CloudFront needs its certificates in `us-east-1`. A few services are allowed for the owner's admin login only. Service Quotas is one, because a higher quota raises the ceiling on spending.
3. **Contain:** an AWS Budgets action attaches a deny-all policy to every episode's CI deploy role (ADR-0011) when actual spend on `portfolio` passes $5. Budgets data lags by hours, so this caps the damage rather than preventing it. It only blocks new deploys, so anything already running keeps costing money. AWS's 2020–21 posts also say the policy detaches itself at the start of the next budget period, even if the cause isn't fixed, so treat it as a monthly limit of about $5 plus the delay. To lift it sooner, reverse the action and then reset it. Detaching the policy by hand can leave the action unable to fire again that month.
4. **Notice:** Cost Anomaly Detection emails when spending departs from the account's normal pattern, even below budget.

Organization-wide Budgets alerts fire at $3 forecast and $5 actual.

Inside each app, the template adds its own limits: a per-IP limit, an API Gateway throttle on all traffic, and a daily spend cap on AI calls. Production's CloudWatch alarms email the owner when the per-IP limit keeps firing or the spend cap is reached.

The approval rule above doesn't apply to `collective-cafe-prod`, where every deploy still needs approval (ADR-0005). That gate protects the café's operation, not its costs. The allowlist does apply there, because it also limits what a compromised role could reach.
