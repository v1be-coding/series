# One CI role per episode, with a permissions boundary

Each episode gets its own CI deploy role, created by the `episodes` stack in `v1be-infra`. Only that episode's repo can assume it through GitHub OIDC, and it can read only that episode's SSM path and write only that episode's state. This extends ADR-0009's rule that one episode can never read another's keys to CI as well as Lambdas. Roles are free, so the isolation costs nothing.

CI may create IAM roles, because the Lambdas and branch environments an agent writes during a run each need one. Every role CI creates must carry its episode's own permissions boundary, generated by `v1be-infra`, so no role CI makes can do more than that ceiling allows. Without the boundary, CI could create an admin role and escape every other limit. The boundary is per episode because a shared one would have to allow every episode's SSM path, which would let one episode's Lambda read another's keys.

## Considered Options

- **One CI role per account:** simpler, but any episode's CI could read every other episode's secrets and state in that account.
- **Lambda roles created ahead of time in `v1be-infra`, with CI limited to `iam:PassRole`:** stronger, because CI could never create a role. We rejected it because a run can't touch `v1be-infra`, so a permission nobody foresaw during Setup would fail the attempt. That works against the one-run rule, and every Lambda in an episode would share one role.

## Consequences

- Every episode resource is named `v1be-<episode>-...` and tagged `episode=<episode>`. AWS needs both, because some resources can only be matched by name and others only by tag. Isolation is still partial: AWS can't scope CloudFront origin access controls or cache policies, so CI gets no write access to them (ADR-0010).
- Trust policies are built in Terraform from numeric org and repo IDs, because repos created after July 15, 2026 use GitHub's immutable `sub` format.
- Portfolio episode roles trust the `pull_request` token of the episode's repo, for branch environments, and `main`. They don't trust every branch, so a branch deploys only through a PR from its own repo, once that PR is ready for review. Draft pushes don't deploy, and PRs from forks are refused. A café episode also gets a role in `portfolio` for its demo. Café roles trust only GitHub's `production` environment, which requires human approval, so AWS itself enforces the ADR-0005 gate.
- CI roles are denied writing SSM, Organizations, Budgets and account settings.
- The ADR-0007 Budgets action attaches its deny-all policy to every portfolio episode role, so its role list comes from the episodes list.
- CI roles don't use `managed_policy_arns` or `aws_iam_role_policy_attachments_exclusive`, because Terraform would remove the Budgets action's deny-all policy on the next apply.
- `v1be-infra` owns the café backup vault and backup role. A café CI role may pass that exact role to AWS Backup and no other, so it can't reach another episode's cluster.
- `org` and `accounts` state lives in the management account, and no CI role has access to that account. `edge` and `episodes` state lives in `v1be-infra-state` in `portfolio`, which no episode role can read, because it holds the origin header and generated secrets (ADR-0012). The other `portfolio` and `collective-cafe-prod` state buckets hold only episode app state.
- `v1be-infra` has its own CI roles, separate from episode roles: a plan role and an apply role in each member account. They have wider rights, including IAM and SSM writes, so they trust only that repo's protected `plan` and `apply` environments and never a branch. The `accounts` stack creates them.
