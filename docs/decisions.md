# Decisions

The numbered decisions from Phase E's grilling session, started 2026-11-06, which built the episode template. Template files, workflows and skills cite them as **Q<n>**, such as "Q40" for frozen tests getting one retry. Decisions that outlived a later change say so in their row. ADRs in `docs/adr/` hold the decisions that shape the whole series. This log holds the template's working rules.

A "private note" is one of the maintainer's research notes, which aren't published. Its conclusion is in the row.

| Q | Decision | Why |
| --- | --- | --- |
| 1 | The agent turns on GitHub auto-merge, and GitHub merges when the required check passes. The bot can't bypass the check or edit the workflow behind it. Café production still waits for the user's approval. The gate test proved auto mode and the bot's token both allow this | GitHub enforces the gate, not the agent's own judgement |
| 2 | A run keeps going after CI fails. The agent reads the public logs and pushes fixes with no human input, for up to 5 failed CI rounds. After that the attempt fails and goes back to the spec | CI also depends on external services, so a single red run shouldn't use up an attempt |
| 3 | A new repo only needs the `org` stack's collaborator grant, as the bot's token already covers all `v1be-coding` repos. Corrected by Q31: the token does need a permission added. Replaced on 2026-11-07: a new repo now needs the App installing on it | An earlier note said "those repos only", which was wrong |
| 4 | The Infracost key is one GitHub organization Actions secret, entered through a `wizard`. Only the Infracost step receives it | It's series-wide and CI-only, and a leak exposes a pricing key, not an account |
| 5 | Branch environments start from `pull_request`: when a PR from this repo is marked ready, then on each later push. Draft pushes don't deploy, and PRs from other repos are refused | One environment per attempt, less CI and DSQL use, no fork path to AWS |
| 6 | Every red CI round counts toward the 5. The workflow retries known temporary failures itself first. If an outage ends an attempt, the user can rule that it doesn't count, and that's logged like a setup fix | The limit stays a plain number |
| 7 | A new `/attempt` command in the template tells the agent to read and follow `implement-spec`, then land the PR: auto-merge, watch CI, fix up to the limit, watch the production smoke test. The stock skill stays unedited | `implement-spec` can't be called by another skill, and instructions in `CLAUDE.md` are easy to skip |
| 8 | When an attempt fails, the agent comments on the spec issue, closes the PR with a `failed-attempt` label and keeps the branch. Closing the PR destroys the environment. The next attempt starts from `main` | Stops the cost, and keeps the failure public |
| 9 | If the production smoke test fails after a merge, the agent opens a fix PR, using the same 5 rounds. If they run out, it opens a revert PR, reopens the tickets, and the attempt fails. This applies to portfolio and café alike. The user chose this over reverting café production straight away | Keeps a working attempt from being thrown away over a production-only problem |
| 10 | The product checklist comes before the merge, on the branch environment. A last job in the required check waits for the user's approval in a GitHub environment. Rejecting it fails the attempt. A new push asks again. Waiting time doesn't count toward time to green. Items about the real domain must be smoke tests | Keeps a failing attempt out of `main`, and matches "every criterion passes" |
| 11 | Episode repos live in a Docker named volume at `/workspaces/v1be/episodes`, not on C:. "No git hooks" stays for everything on C:. Git hooks are allowed in the volume | The rule exists because Windows could run planted hooks in a bind-mounted repo. Windows can't reach the volume |
| 12 | Template guardrails block pushing to `main`, force pushes, `reset --hard`, `git clean -f`, `branch -D`, and `gh pr merge` without `--auto`. Ordinary branch pushes stay allowed. It's a hook in the template's `.claude/settings.json` | Catches mistakes early. GitHub still enforces the merge rules |
| 13 | The required check is one chain: lint, type checks and unit tests → Infracost, with approval if over $1 → branch deploy → smoke test, frozen acceptance tests and evals → `checklist` approval → `green`, which always runs and fails unless all before it succeeded. Acceptance tests, the smoke test and eval thresholds are frozen: written in the Spec phase, merged to `main` before the run, and CI runs them from the PR's base commit. A wrong frozen test is a spec failure and fails the attempt. No separate flag for edited unit tests | A run can edit the tests it's judged by. Keeping them outside its reach enforces the gate, and Rule 3 already sends a wrong spec back |
| 14 | `account = "cafe"` means two targets: `episodes` creates two CI roles and a `<subdomain>-demo` address in `portfolio`. On merge the demo deploys and passes its smoke test, then production waits for the user's approval, then its smoke test runs. The template picks targets from the episode's account | ADR-0005 needs a public demo and an approved production |
| 15 | The user learns of a waiting approval from GitHub's own notifications. The agent also comments on the PR with the branch URL and the checklist | No extra tools |
| 16 | The dev container gets pinned Node, Chromium's system libraries and a larger `/dev/shm`, in a `v1be-infra` PR with the volume change. Each repo pins its own Playwright version and downloads its own browser. Proven in the Phase E slice that adds the frontend | There's no Node or browser support today. The agent should check its work before pushing |
| 17 | Each branch environment gets its own DSQL cluster, with seed data loaded after migrations, destroyed with the branch | "Complete deployment" in the glossary, and clean teardown |
| 18 | The portfolio page stays out of the template plan. How pages get published is settled during episode 0, as a PR to the site's repo after Ship | The site doesn't exist yet, and the page includes the user's own writing |
| 19 | Code owner review protects the frozen folder and `CODEOWNERS`, with no other required reviews, so a normal run never triggers it. A PR that changes only the frozen folder skips the deploy and goes to `green`. Proven by the gate test on 2026-11-06, as GitHub's docs don't cover it | Otherwise a run's edit to a frozen test reaches `main`, and production and the next attempt use the weakened copy |
| 20 | New `/acceptance` command in the template. Spec phase becomes `/to-spec` → `/to-tickets` → `/acceptance`. It writes frozen tests from the spec, sets eval thresholds and opens the PR. Each test must fail on `main` first | Stock skills don't do this, and a test that passes before any code exists proves nothing |
| 21 | The frozen smoke test checks four things: the page loads through Cloudflare in a real browser, the API answers through the page, a write and read reach the database (read-only on café production), and going over the per-IP limit gives a handled 429. No real AI call: evals cover that. The template ships Playwright, Vitest and a sample test of each | Proves the whole stack on every deploy, at no AI cost and with no real data written |
| 22 | CI counts failed runs on the PR's branch and stops at 5, in the first job. Runs don't cancel each other. A rejected approval fails the attempt outright, and waiting isn't a failed round. A Q9 fix PR is a new branch, so its count starts fresh | The limit stays out of the agent's hands |
| 23 | The `org` stack sets each episode repo's auto-merge, branch protection, code owner review, bot access (now the App's installation, which `org` doesn't set) and `checklist` environment, plus the same for the template repo. The user runs it in Windows Sandbox at Setup, after creating the repo | These need an admin login, which CI doesn't have |
| 24 | A run can stop early if a frozen test looks wrong, naming the test and its reason on the spec issue. It still counts as a failed attempt, and the test is fixed in a spec PR before the next attempt | Saves rounds on a failure that's already certain, with nothing to gain from giving up |
| 25 | The template plan starts with a gate test on `episode-template`, before any slices: `org` sets the rules, then two small PRs prove code owner review at 0 approvals, the bot enabling auto-merge, auto mode allowing `gh pr merge --auto`, and auto-merge waiting for the check and approval. The user types the merge steps. The browser in the frontend slice, and the `pull_request` token in the Lambda slice | The riskiest assumptions are GitHub's, so they're tested before anything is built on them |
| 26 | Order: `series` PR → `v1be-infra` PR (container changes, the template repo's `org` rules) → gate test → slices. `deploy.yml` for `episodes` comes with the first slice that needs it. If the gate test changes Q19, a small follow-up PR corrects ADR-0013 | The rules are recorded before they're built |
| 27 | Glossary: **Run** now covers the whole `/attempt`, including landing and fixing. New **Frozen test**: a test written during the Spec phase that the run can't change, covering acceptance tests, the smoke test and eval thresholds. New **Round**: one CI pass that ends in failure, at most 5 per attempt | The terms changed with the workflow |
| 28 | `/retro` reads the scorecard from GitHub. Time to green: run start to `green`, minus approval waits. Attempts: PRs labelled `failed-attempt`, plus one. Tests passing on attempt 1: frozen tests passing on attempt 1's first CI run. Build cost and model used stay as they are | Hand counts are a weak spot when the result must be honest |
| 29 | No scaffolding. `/acceptance` runs in a fresh session that reads only the spec and writes a test contract: routes, request and response shapes, roles, names, visible text and any data that must already exist. The user reviews the contract and tests together. Each assertion must trace to a contract line. Tests find things by role, name and visible text, with test IDs as the exception. They create data through routes the contract names, and the run loads listed seed data. Everything they use, including config and helpers, comes from the base commit. They run only on the branch environment; production keeps the smoke test. This replaces the failure-reason idea in Q20's first draft: a test must still fail on `main`, but that proves little | the private note `research-tests-before-code-for-agents.md`: independence and stated interfaces have the best evidence, and scaffolding would weaken Rule 1 |
| 30 | No throwaway reference build and no hidden test suite for now. `/retro` records how many frozen tests turned out wrong, so a reference build can be added if they keep costing attempts | A reference build costs about a run. Hidden tests lowered legitimate results in one benchmark, and public logs could leak them |
| 31 | The bot's token gains Issues read and write. Replaced on 2026-11-07: the App has Issues write. The user updates it in Windows Sandbox, and `sandbox/wizards/github-org.sh` changes in the `v1be-infra` PR | Creating an issue needs `issues=write`, and the bot files the spec and tickets, which the series publishes as GitHub Issues |
| 32 | `/setup-matt-pocock-skills` runs once on the template, not per episode. The `org` stack creates `failed-attempt`; Q35 removes triage labels | The skill writes ordinary files that every episode inherits. Labels live on the repo |
| 33 | The Spec phase says "`research` or `field-reports` as needed": `research` for documented facts, `field-reports` for real-world behaviour. `/research` stays installed. `field-reports` is an optional step, as it lives in the user's account and not in a repo | `field-reports` points to `research`, and `wayfinder` calls `research` by name |
| 34 | `/attempt`'s PR comment reminds the user to try their own values, not the ones in the tests | Hard-coded answers pass frozen tests but fall apart on other values |
| 35 | The template ships `grill-with-docs`, `grilling`, `domain-modeling`, `to-spec`, `to-tickets`, `implement-spec`, `tdd`, `code-review`, `retro`, `research`, `wizard`, `pr`, `diagnosing-bugs`, `codebase-design` and `writing-for-agents`, plus `/attempt` and `/acceptance`. Other skills stay in the workspace, for sessions started in `/workspaces/v1be`. `triage` is left out, so setup skips triage labels and `org` only creates `failed-attempt` | Most installed skills overlap, are replaced by the template, or don't fit this workflow. Nothing kept depends on a skill left out |
| 36 | The template carries a pinned copy of those skills in `.claude/skills`, with `SOURCES.md` recording the commit, and keeps upstream's MIT notice and `pr`'s `CREDITS.md`. Updates are by hand | Claude Code loads parent skills only up to the repository root, so the workspace copy doesn't reach an episode repo. Official plugin marketplaces update automatically, which would muddy comparisons between episodes |
| 37 | Runs keep `tdd` for now, through `implement-spec`. `/retro` records build cost, and this is reviewed after episode 1 | One study found no clear gain at 3 to 8.5 times the tokens, but on a different stack, and dropping it means changing how `implement-spec` runs |
| 38 | `/attempt` states a rule: if a frozen test looks wrong, stop and report, and never change app behaviour just to satisfy it. The report quotes the test and the contract line it conflicts with. It's still a failed attempt | the private note `field-reports-frozen-tests.md`: an agent barred from editing a buggy test changed production login instead, and "stop and report" prompts had the best controlled result |
| 39 | `/acceptance` and CI reject frozen tests that contain `if`, early `return`, `try`, `.skip`, `.only` or `.fixme`, or that have no assertion | Agent-written Playwright tests were reported returning early and passing. It lives in CI, so the agent can't turn it off |
| 40 | Frozen tests get one retry. A test that needed it counts as a pass and is listed in the PR comment and the retro | Default retries hide flakes, and a Lambda cold start can cause a real one-off failure |
| 41 | `episodes` owns each production distribution, site bucket, API shell, certificate and DNS, and the template only publishes into them. A run can't change production routing, which is fixed at `/` and `/api/*` | A role that can edit a distribution could remove the header check and read the series-wide origin secret. It also gives DNS a target before the first deploy |
| 42 | Anything a portfolio episode stores, on its live site too, is disposable and never Real data. An episode that wants lasting data on `portfolio` needs its own ADR | ADR-0005 keeps Real data in `collective-cafe-prod`, so the worst case is a broken site and a redeploy |
| 43 | The template's `infra/` creates every target's DSQL cluster, including production's. No cluster lives in `v1be-infra` | Q41's reason was the origin secret, and a cluster has none. Slice 4 needs runs to create and delete clusters anyway |
| 44 | Seed data loads on every `portfolio` target, including live sites and café demos, and never on café production. It's decided by target, not episode. An episode that wants no sample rows leaves its seed file empty | ADR-0005 is wider than Q17, café demos need data, and slice 3 can prove the step |
| 45 | Production clusters have deletion protection on, and no CI role gets `dsql:UpdateCluster`. Branch clusters stay unprotected. Changing cluster settings or retiring a production cluster needs the user's admin login | The guard must sit outside files a run can edit, so `prevent_destroy` doesn't count. The provider only turns protection off through `UpdateCluster`. It stops a Terraform mistake taking down a live site, at no cost |
| 46 | One CI role stays, and from slice 4 a ready PR can reach a portfolio site's database as admin. This is an accepted known risk. Café production isn't exposed, as its role only trusts the approved `production` environment | Q42 makes that data disposable, and a second role changes ADR-0011 and adds a role per episode to protect it |
| 47 | A check in `deploy.yml` fails the deploy if a migration contains `DROP`, `TRUNCATE`, `RENAME`, `ALTER COLUMN ... TYPE`, `DELETE` or `UPDATE`. It's a plain text match, and false matches on comments are accepted | ADR-0013's add-only rule needs enforcing where a run can't edit it, and a revert can't undo a migration on café production |
| 48 | The template tags the cluster `backup=weekly` when the target is café production. A guard against removing the tag waits for the first café episode | The tag sits in a file a run can edit, but a change still needs production approval, and nothing in slice 3 targets café to test a guard |
| 49 | The Lambda connects as one custom database role with `SELECT`, `INSERT`, `UPDATE` and `DELETE` on tables and no schema rights. `deploy.yml` runs migrations, then a masked step that creates the role, maps it to the Lambda's role and grants table rights, then seed, all as admin. The grant step reruns on every deploy | The running app shouldn't hold admin rights. `AWS IAM GRANT` contains the account ID, so it can't go in a committed migration in a public repo |
| 50 | A branch environment is named `pr-<number>`, with state at `<episode>/pr-<number>/terraform.tfstate`, and lives in `portfolio` for every episode. `infra/` makes its API, bucket `v1be-<episode>-site-pr-<number>` and distribution | PR numbers are short, stable and not attacker-controlled, unlike branch names |
| 51 | CI may write only distributions tagged with its own episode, and is explicitly denied any write to a distribution tagged `stack=episodes`, which every `v1be-infra` distribution carries. Portfolio roles only. A real PR token must be refused a no-op update on production before any branch deploys. Without that proof, slice 4 stops. Proven on 2026-11-07, run 42353155971 | ADR-0010's risk is a role editing production's distribution. AWS's reference lists `aws:ResourceTag` on distributions, but that's untested here |
| 52 | Branch APIs get no throttle before slice 5. Slice 5's per-IP limit must find the client IP without Cloudflare's header | The user chose to keep branch infra the same as production. Environments are short-lived, text is capped at 1,000 characters, and the Budgets action is the backstop |
| 53 | CI's tag rights can't take over another episode's resource, fixed in slice 4's `v1be-infra` PR. Clusters: `dsql:TagResource` also requires that any existing `episode` tag is CI's own. APIs: AWS's reference gives `/tags/*` no condition keys, so the unconditioned right is removed and tags are set at creation | Without this, one portfolio episode could re-tag another's cluster or API and take it over, which breaks ADR-0011 |
| 54 | Deploy steps shared by branch and production go in a reusable workflow under `.github/workflows/`, never a composite action. Teardown runs `main`'s `infra/` and deletes the state file, so leftover `pr-*` state with a closed PR marks an orphan for the weekly job | The App can't write `.github/workflows/`, but it can write `.github/actions/`. A closed PR's merge ref can be stale or conflicted |
| 55 | Close the raw `execute-api` address on every target. CloudFront adds a secret origin header, one per target, and the Lambda returns 403 without it, before any counter is touched. Production's secret is generated per episode in `v1be-infra`, and branches generate their own. The Lambda picks the client IP by target, never from the request: `sourceIp` on branches, and `CF-Connecting-IP` on production, trusted only after the origin header check. #24 showed `sourceIp` is the real caller on a branch on every path, even with forged headers, and that `CF-Connecting-IP` passes through CloudFront untouched. Production's first deploy confirms `sourceIp` there is a Cloudflare address. An API Gateway stage throttle of about 10 requests a second also caps all traffic combined. A temporary PR logs the real headers on a branch first, and production's header is checked on its first deploy | The per-IP limit trusts a header, and the raw address lets a caller write it. The existing `v1be-origin-check` only guards CloudFront's own address. Nothing else caps traffic spread across many IPs, and Budgets only stops deploys |
| 56 | Rate-limit and spend-cap counters live in DynamoDB, one table per target made by the template's `infra/`, with expiring rows. `dynamodb` joins the SCP allowlist, and CI and the boundary get rights scoped to `v1be-<episode>-*` tables. Needs an `org` run in the Sandbox | Atomic counters at about $0.71 per million writes (third-party figure). DSQL would add a write and 40001 conflicts to every request and use the shared DPUs, Lambda memory counts per instance, and WAF isn't on the allowlist |
| 57 | The browser uses one shared `api()` wrapper. On any 429, from the app, API Gateway or Cloudflare, it shows "try again in N seconds" and doesn't retry by itself. The 4th smoke check confirms that message on the page | A limited visitor should see why, not a page that looks broken. Every episode reuses it |
| 58 | Infracost reads the PR's and the base's `infra/` with no plan and no AWS login, using CLI v0.10.47 pinned by hash. The key goes only to that step, and the result goes in the job summary. Over $1, a separate job naming the `cost` environment waits for approval. The deploy job never names an environment, and still runs when that job is skipped. If Infracost is down after retries, it asks for approval rather than failing a round. Proved with a temporary PR adding two KMS keys, then rejected | Naming an environment on the deploy job changes the token's `sub`, which the CI role refuses |
| 59 | The per-IP limit is 120 requests a minute on every `/api/*` route, with a per-route override, a JSON 429 and `Retry-After`. IPs are stored hashed, IPv6 by /64, and a counter error lets the request through. Frozen tests pace themselves: one fixture lets at most 100 API calls through in any 60 seconds, with `workers: 1`, a request budget per test, any 429 failing an acceptance test, and `retryStrategy: 'isolated'`. `failOnFlakyTests` stays off, so Q40 stands: a retried test passes and is reported, with `trace: 'retain-on-failure-and-retries'`, which keeps the failed attempt, to judge it. How to label flaky or real failures goes to the private note `research-flaky-or-real-failures.md` for slice 6's reporter. The 4th smoke check sends up to 121 requests at 4 a second to `GET /api/health`, with its own longer timeout, runs last in its own project on a fresh window, and checks the page's message. The Q39 lint allows the fixture | the private note `research-e2e-tests-and-rate-limits.md`: Playwright has no retry on status, and waiting on a 429 can't tell normal test traffic from an app flooding its API. Cloudflare blocks above 50 in 10 seconds, so the smoke check must trip ours first. Pacing keeps tests under the same limit as users. 120 stays under the smoke check's 240 a minute and Cloudflare's 300, and one IP gets at most a fifth of the throttle |
| 60 | AI spend has three layers. A template helper keeps a daily dollar counter per target in DynamoDB, reserving the worst-case cost before each call and refunding the rest after, with UTC days and a default of $1 a day per target, which an episode can lower in its spec. At the cap the AI feature returns a distinct 429 and the rest of the app keeps working, and a counter error refuses the call. Low workspace rate limits are set by hand at Setup as a ceiling, and the monthly workspace spend limit is the last stop. The admin key stays out of the app and CI. Unit tested only until the first episode with an AI call, listed in phase F | the private note `research-ai-daily-spend-cap.md`: Anthropic has no daily dollar cap, spend limits are monthly, `tokens_per_day` is undocumented, and usage reports lag 5 minutes to 24 hours |
| 61 | Two CloudWatch alarms per production target, none on branches: more than 50 rate-limit 429s in 5 minutes, and the spend cap reached. The Lambda writes both metrics as EMF in its log line, with the hashed IP as a plain field, never a dimension. They email through one SNS topic per member account, owned by `v1be-infra`'s `accounts` stack. `sns` joins the allowlist in the same `org` run as `dynamodb`. The `accounts` stack subscribes the email, as it already does for anomaly alerts. It only runs in the Sandbox, so the address stays out of public logs. `accounts-apply.sh` confirms it with `--authenticate-on-unsubscribe`. CI gets the topic ARN as a plain value and no SNS rights, and may only create alarms named `v1be-<episode>-*` whose actions are that topic (`cloudwatch:AlarmActions` with a `Null` check). A test confirms CI can't point an OK action at another topic | the private note `research-alarm-email-warnings.md`: about $0.20 a month per target, inside the organization's 10 free alarms for up to 5 episodes. Alarms only email on a state change. The provider prints a subscription's email in the plan |
| 62 | The chain lives in `deploy.yml`, and `gate-test.yml` is removed in the same PR: `rounds` → `checks` and `cost` side by side → `cost-approval` (waits for both) → `deploy` → `verify` → `checklist` → `green`. `verify` is its own job with no AWS token, running `frozen/` from the base commit against the branch URL. Production's smoke test after a merge uses the same steps with `main`'s `frozen/` and no traces. `green` never skips on a PR: it fails on drafts and fork PRs. A new push cancels the older run's waiting `checklist` through job-level concurrency. No retries are added to deploy steps until a real failure calls for one | GitHub treats a skipped check as passing, and `gh pr merge --auto` merges at once on a mergeable PR (gate test), so a draft's skipped `green` could merge in the moment after it's marked ready (Inferred, tested live in slice 6). Frozen tests need no AWS access |
| 63 | A round is a failed run of `deploy.yml` on the PR's branch in which `rounds`, `checks`, `cost`, `deploy` or `verify` failed. Runs where only `checklist` and `green` failed don't count | A rejected checklist already ends the attempt (Q22), and a cancelled stale checklist isn't the agent's failure |
| 64 | The frozen lint is a script in `frozen/` that reads the syntax tree with the TypeScript compiler, added to `frozen/package.json`. It bans Q39's list plus `?:`, `switch`, `.catch()` and `.fail` (confirmed by the user on #32), and exempts `frozen/helpers/`. CI runs it from the base commit, on the base's `frozen/` normally and on the PR's own in a frozen-only PR | A text match trips on comments and titles and can't find a test with no assertion. Ternaries, `switch` and `.catch()` leave the same loophole open as `if` and `try` |
| 65 | `checks` runs actionlint, downloaded in CI and pinned by sha256, with shellcheck off at first. No app linter in this slice: ESLint is chosen in slice 7 with the pre-commit hooks | actionlint catches the workflow-format errors that merged in #17, which a YAML parse misses. Auto mode refuses only Claude running it locally |
| 66 | The frozen PR lands before the workflow PR, because `verify` runs the reporter from the base commit. It holds the lint, the evidence fixture, the retry reporter and the JSON reporter. The reporter always writes the job summary, and posts one PR comment, updated in place, only when a test was retried or failed. Hints are `infra-looking`, `app-looking` or `unclear`, defaulting to `unclear`, beside the evidence and never as verdicts. Traces are uploaded from branch environments only, kept 7 days. Results JSON is kept for the slice 7 retro | the private note `research-flaky-or-real-failures.md`, option C with E and F |
